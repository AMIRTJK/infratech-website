# AGENTS.md — правила разработки `infratech-website`

Единственный источник правил для разработчиков и AI-агентов.
`CLAUDE.md` и `GEMINI.md` — тонкие указатели на этот файл, дублировать в них правила нельзя.

**Приоритет источников при конфликте:** явная просьба пользователя → этот файл → `PERFORMANCE.md` (frontend) / `server/PERFORMANCE.md` (backend) → `docs/ARCHITECTURE.md` → существующий код рядом с правкой.

---

## 1. Проект

**Что это.** Публичный сайт организации: информационный сайт/лендинг. Рассказывает об организации, её деятельности, услугах, проектах, команде, контактах; принимает обращения через форму обратной связи. Это **не** CRM и **не** внутренняя система — здесь нет ролей, прав доступа, реестров и рабочих процессов сотрудников.

**Следствия для архитектуры** (их важно держать в голове при любом решении):

- Аудитория — анонимные посетители с мобильных устройств и слабых сетей. **Скорость первой загрузки и SEO — функциональные требования, а не «оптимизация потом».**
- Контента много, интерактива мало. По умолчанию страница — статическая или серверно отрендеренная; клиентский JavaScript добавляется точечно.
- Публичный периметр: любая ручка backend доступна из интернета. Валидация, ограничение частоты запросов и защита формы от спама обязательны с первого дня.

**Язык интерфейса, контента, документации и коммитов — русский.**

## 2. Стек и разделение репозитория

Репозиторий — монорепозиторий из двух **независимых** приложений. Workspaces не используем: у каждой части свои зависимости и своё дерево `node_modules`, каждая ставится и запускается сама по себе. Корневой `package.json` — только оркестрация (запуск обеих частей одной командой) и никаких зависимостей приложения.

```
infratech-website/
├── client/   — только frontend: Next.js 15 (App Router) · React 19 · TypeScript 5.9 (strict) · Tailwind CSS 4
├── server/   — только backend:  Node.js 22+ · TypeScript 5.9 (strict) · Fastify · better-sqlite3 · Nodemailer
├── docs/     — архитектура, анализ зависимостей, дизайн-документы
├── package.json       — оркестрация: npm run dev поднимает обе части
├── AGENTS.md          — этот файл, правила разработки
├── PERFORMANCE.md     — производительность frontend
└── server/PERFORMANCE.md — производительность backend
```

**Жёсткие границы:**

1. В корне репозитория не размещается код приложения — только документация, общие для репозитория конфиги (`.gitignore`, `.editorconfig`, `.nvmrc`) и оркестрационный `package.json`. Зависимости приложения в корень не добавляются: пакет для фронтенда ставится в `client`, для бэкенда — в `server`.
2. Frontend-код существует только в `client/`, backend-код (API, SQLite, Nodemailer) — только в `server/`.
3. **Backend не размещается внутри Next.js.** Route Handlers (`client/src/app/api/**`) не используем для бизнес-логики: доступ к базе, отправка писем и любые обращения к внешним системам живут в `server/`. Допустимое исключение — технические ручки самого фронтенда (например, приём Web Vitals), и только по согласованию.
4. Части общаются **только по HTTP через публичный API** `server`. Общего кода между `client` и `server` нет: типы контракта дублируются осознанно (см. §10).

## 3. Команды

**Из корня — обе части одной командой.** Корневой `package.json` содержит только оркестрацию (`concurrently`) и не имеет отношения к коду приложения: он вызывает скрипты `client` и `server`, а не заменяет их.

```bash
npm install        # ставит зависимости корня, client и server (postinstall)
npm run dev        # поднимает обе части: client :3000 и server :4000 в одном терминале
npm run build      # сборка обеих частей
npm run start      # запуск прод-сборок обеих частей
npm run typecheck  # проверка типов в обеих частях
npm run lint       # линт в обеих частях
```

`npm run dev` из корня запускает процессы с префиксами `client`/`server` в общем выводе; `Ctrl+C` останавливает оба (`concurrently -k`). Для сосредоточенной работы над одной частью удобнее её собственный терминал — тогда логи не перемешиваются, а перезапуск не трогает соседа.

Каждая часть при этом остаётся самостоятельной и запускается из своей директории.

```bash
cd client
npm install
npm run dev        # Next.js dev-сервер, http://localhost:3000
npm run build      # прод-сборка (включает проверку типов)
npm run start      # запуск прод-сборки
npm run typecheck  # tsc --noEmit
npm run lint       # eslint
npm run analyze    # сборка с анализом бандла (@next/bundle-analyzer)
```

```bash
cd server
npm install
npm run dev        # tsx watch, http://localhost:4000
npm run build      # tsc -> dist/
npm run start      # node dist/app/main.js
npm run typecheck  # tsc --noEmit
npm run lint       # eslint
npm run test       # node --test
```

Фронтенд и бэкенд остаются **двумя независимыми приложениями**: свои зависимости, своя конфигурация, свой процесс. Корневой скрипт — удобство запуска, а не объединение частей. Общих зависимостей, workspaces и общего кода между `client` и `server` по-прежнему нет, и они не появляются без согласования.

Тестовый фреймворк (Vitest/Jest) не подключён. Тесты `server` — на встроенном раннере Node (`node --test`) и покрывают то, что проверяется без сети и DOM: чистые функции, валидацию, сборку запросов. Тесты добавляются вместе с кодом, который они проверяют, а не заранее.

**Запуск полной прод-сборки (build) и браузерное/визуальное тестирование выполняем только по явной просьбе пользователя.** Быстрые статические проверки (`typecheck`, `lint`) агент обязан выполнять перед завершением задачи (см. §20).

## 4. Архитектура frontend: FSD поверх App Router

Клиент строится по **Feature-Sliced Design**, адаптированному под Next.js. Директория `src/app/` занята маршрутизацией Next, поэтому слой FSD `pages` переименован в **`views`** — это рекомендованный способ совмещения FSD с App Router.

Импорт разрешён **только вниз**, никогда вверх и никогда вбок между модулями одного слоя:

```
app (маршруты Next) → views → widgets → features → entities → shared
```

| Слой | Ответственность | Запрещено |
|---|---|---|
| `src/app/` | Только маршрутизация Next: `layout.tsx`, `page.tsx`, `loading.tsx`, `error.tsx`, `not-found.tsx`, `sitemap.ts`, `robots.ts`, метаданные. Файл роута тонкий: собрать метаданные, получить параметры, отрендерить `view`. | Разметка экранов, бизнес-логика, прямые запросы к API |
| `src/app/_providers/` | Клиентские провайдеры (`QueryClientProvider`, тема, `ErrorBoundary`). Подчёркивание делает папку приватной для роутера Next. | Всё остальное |
| `src/views/` | Экран целиком: собирает layout и виджеты, владеет серверными данными страницы | Дублирование логики виджетов |
| `src/widgets/` | Крупные самодостаточные блоки страницы: шапка, футер, hero, секция услуг, блок контактов | Импорт из `views` и `app` |
| `src/features/` | Законченный пользовательский сценарий: форма обратной связи, переключатель темы, поиск по разделу | Импорт из `widgets`, `views`, `app` |
| `src/entities/` | Доменные типы и мелкие представления сущностей: услуга, новость, сотрудник, проект | Любые импорты выше `shared` |
| `src/shared/` | Инфраструктура: `api/`, `config/`, `lib/`, `ui/`, `types/`, `styles/` | Любая доменная логика и импорты из верхних слоёв (включая `import type`) |

**Псевдонимы путей** (`client/tsconfig.json`): `@app/*`, `@views/*`, `@widgets/*`, `@features/*`, `@entities/*`, `@shared/*`. Относительные пути — только внутри одного модуля.

**Общие типы и правило чистоты `shared`:**
- В `shared` строго запрещён любой импорт из верхних слоёв (`@features`, `@entities`, `@widgets`, `@views`, `@app`), **включая `import type`**.
- Общие типы приложения (тема оформления `TTheme`, локали `TLangCode`, глобальные union'ы, структуры ответов API), которые нужны в `shared/ui` или более чем в одном модуле/фиче, **обязательно объявляются в `@shared/types/`**, а не внутри конкретной фичи.
- Модули верхних слоёв импортируют общие типы из `@shared/types/`, предотвращая межфичевые зависимости и циклы.

**Публичный API модуля.** Наружу модуль виден через свой `index.ts`. Импорт из чужого модуля идёт на корень (`@widgets/ContactsSection`), а не вглубь (`@widgets/ContactsSection/ui/MapBlock`). Внутри модуля глубокие пути нормальны.

**Поток данных — вниз через пропсы.** Данные получает владелец экрана (`view` или серверный компонент виджета) и передаёт вниз. Одни и те же данные не запрашиваются дважды с разных уровней.

**Слабая связанность.** Модуль общается с внешним миром только через пропсы и колбэки. Общее поднимается в `shared` или `entities`.

## 5. Структура модуля frontend

```
ModuleName/
  index.ts        # публичный API: только то, что нужно снаружи
  ui.tsx          # главный компонент (или ModuleName.tsx — следуй соседям)
  ui/             # подкомпоненты, каждый в своём файле
  model.ts        # типы, константы, схемы валидации, доменные union'ы
  lib.ts | lib/   # чистые функции, хелперы, хуки модуля
  api/            # запросы модуля (если их больше пары)
  style.css       # локальные стили модуля (только если Tailwind выражает плохо)
```

## 6. Архитектура backend

`server` — самостоятельное Node-приложение со слоистой модульной структурой. Слои внутри модуля: **route → controller → service → repository**. Обратные зависимости запрещены: репозиторий ничего не знает о HTTP, сервис — о Fastify.

```
server/src/
  app/            # бутстрап: main.ts (точка входа), сборка сервера, регистрация плагинов и модулей, graceful shutdown
  config/         # чтение и валидация переменных окружения, единый типизированный объект config
  modules/        # доменные модули API, по одному на ресурс
    <module>/
      <module>.routes.ts      # объявление маршрутов и схем запроса/ответа
      <module>.controller.ts  # разбор запроса, вызов сервиса, формирование ответа
      <module>.service.ts     # бизнес-логика, без знания о HTTP
      <module>.repository.ts  # доступ к SQLite, единственное место с SQL
      <module>.schema.ts      # zod-схемы входа/выхода, типы контракта
      index.ts                # публичный API модуля (плагин Fastify)
  db/             # подключение к SQLite, применение миграций, seed
    migrations/   # нумерованные SQL-миграции, только вперёд, никогда не редактируются задним числом
  mail/           # транспорт Nodemailer, отправка писем
    templates/    # шаблоны писем
  middlewares/    # общие плагины и хуки: обработка ошибок, rate limit, CORS, логирование, request-id
  shared/         # утилиты, общие типы, константы, доменные ошибки
  types/          # общие типы приложения и расширения типов Fastify
server/data/      # файл базы SQLite (в git не попадает; попадают только миграции)
server/tests/     # node --test
```

**Правила backend:**

1. **Единственное место с SQL — `*.repository.ts`.** Ни контроллер, ни сервис, ни `mail/` не обращаются к базе напрямую.
2. **Валидация входа обязательна для каждой ручки** — zod-схема (или JSON Schema Fastify) на `body`, `query` и `params`. Ничего невалидированного до сервиса не доходит.
3. **Никаких строковых конкатенаций в SQL.** Только подготовленные выражения с параметрами.
4. **Ошибки — доменные классы + единый обработчик** в `middlewares/`. Наружу уходит понятное сообщение и код; стек и внутренние детали — только в лог.
5. **Секреты — только из окружения** (`config/`). Ключей, паролей SMTP и путей к базе в коде быть не может.
6. **Отправка писем — только через модуль `mail/`.** Прямых вызовов `nodemailer` из модулей API нет; отправка не задерживает ответ клиенту (см. `server/PERFORMANCE.md`).
7. **Публичные ручки защищены**: rate limit, ограничение размера тела запроса, honeypot/капча на формах, CORS с явным списком разрешённых источников.
8. **Проект на ESM** (`"type": "module"`, `moduleResolution: NodeNext`): относительные импорты пишутся с расширением `.js`, даже когда файл — `.ts` (`import { config } from "../config/config.js"`). Псевдонимы путей на сервере не используем — они требуют дополнительного резолвера в рантайме.

## 7. Лимит размера файла — 250 строк

**Целевой предел: ~250 строк на любой файл** (`.ts`, `.tsx`, `.css`) в обеих частях проекта. 250 — не обрыв на 251-й строке, а порог, после которого нужно осознанно решить: декомпозировать сейчас или зафиксировать причину.

- **до 250** — норма;
- **250–400** — жёлтая зона: декомпозируй, если правишь этот файл по задаче;
- **свыше 400** — красная зона: новый код такого размера не принимается.

**Исключение — файлы-данные.** Лимит не применяется к файлам из данных без логики: тексты контента, справочники констант, токены темы, наборы типов, реестры маршрутов (`ApiRoutes`, `AppRoutes`), SQL-миграции. Дробить их вредно — теряется единая точка поиска.

### Как декомпозировать (по приоритету)

1. **Подкомпоненты.** Самостоятельный кусок JSX со своим смыслом (шапка секции, карточка, футер формы) → отдельный файл в `ui/`. Признак: у куска есть имя, которое произносишь вслух.
2. **Хуки.** Связка состояния и эффектов вокруг одной темы → `useSomething()` в `lib/`.
3. **Данные.** Запросы и нормализация ответа → `api/`. Компонент не должен знать формат ответа сервера.
4. **Чистые функции.** Форматирование, сортировка, маппинг → `lib.ts`.
5. **Типы и константы.** → `model.ts`.
6. **Конфигурация вместо разметки.** Однотипные карточки, поля формы, пункты меню → массив-описание + рендер в цикле. Пятнадцать похожих блоков подряд — это данные, а не код.

На backend порядок тот же: маршрут → контроллер → сервис → репозиторий; разросшийся сервис делится по сценариям, а не механически.

### Чего делать нельзя

- Резать файл на `part1.tsx` / `part2.tsx` ради счётчика строк.
- Создавать «файл-мешок» `helpers.ts` со всем подряд.
- Разносить состояние по подкомпонентам так, что родитель перестаёт понимать экран: состояние живёт у владельца, вниз идут значения и колбэки.

## 8. Именование

- **Компоненты** — `PascalCase`, файл называется как компонент (`ContactForm.tsx`), либо `ui.tsx` для главного компонента модуля.
- **Хуки** — `useCamelCase`, один хук на файл.
- **Функции, переменные** — `camelCase`; **константы-справочники** — `UPPER_SNAKE_CASE`.
- **Интерфейсы** — префикс `I` (`IProps`, `IContactRequest`). Локальные пропсы компонента — `IProps`; экспортируемые — осмысленное имя.
- **Type-алиасы** — префикс `T` (`TLocale`, `TSectionKind`).
- **Булевы значения** — `is…`, `has…`, `can…`, `should…`.
- **Обработчики** — `handleXxx` внутри компонента, `onXxx` в пропсах.
- **Файлы backend** — `kebab-case` с суффиксом слоя: `contact.service.ts`, `contact.repository.ts`.
- **Таблицы и колонки SQLite** — `snake_case`, таблицы во множественном числе (`contact_requests`).
- **Миграции** — `NNN_краткое_описание.sql` (`001_init.sql`), нумерация строго по возрастанию.
- **CSS-классы — стандартный БЭМ:** `block__element--modifier`, блок префиксуется зоной ответственности (`ui-`, имя модуля). По умолчанию стилизуем Tailwind-утилитами, а не классами (см. §13).

## 9. TypeScript

- `strict: true` в обеих частях — не обходим его через `@ts-ignore`, `as any`, `!` на пустом месте.
- **Код без `any`.** Не знаешь тип — `unknown` + сужение, либо опиши интерфейс.
- Union'ы вместо «магических» строк: `type TLocale = "ru" | "en"`.
- `enum` не используем — `as const`-объект предпочтительнее (так объявляются `AppRoutes` / `ApiRoutes`).
- Никаких «магических» строк и чисел в логике: тексты, лимиты, ключи хранилищ — в `model.ts` модуля, `shared/config` или `server/src/config`.
- Типы ответов API описываем рядом с запросом или в `model.ts` модуля; общие доменные типы — в `entities/*/model.ts` (client) и `<module>.schema.ts` (server).

## 10. Данные и API

**Контракт.** REST с версией: `/api/v1/<resource>`, `/api/v1/<resource>/:id`, вложенные действия — `/api/v1/<resource>/:id/<action>`.

**Формат ответа — единый конверт:**

```ts
{ success: boolean; message: string; data: T }
```

Ошибки отдаются тем же конвертом с `success: false`, осмысленным `message` на русском и корректным HTTP-статусом; детали валидации — в `data`.

**Frontend:**

- **URL API — только из `ApiRoutes`** (`client/src/shared/api/api-routes.ts`), маршруты страниц — только из `AppRoutes` (`client/src/shared/config/app-routes.ts`). Хардкод путей запрещён.
- **Базовый адрес backend — только из конфигурации** (`NEXT_PUBLIC_API_URL` для браузера, `API_INTERNAL_URL` для серверных компонентов), читается в одном месте — `shared/config`. `localhost:4000` в коде компонентов не встречается.
- **Чтение контента — на сервере.** Серверные компоненты и `views` получают данные через `fetch` с осознанными `cache`/`revalidate`. Это быстрее и лучше для SEO, чем клиентский запрос.
- **Клиентские запросы — через TanStack Query v5** (`useQuery` / `useMutation`) и общий HTTP-клиент из `shared/api`. Прямые `fetch`/`axios` в компонентах — только для нестандартных случаев (например, скачивание файла).
- Ключи кэша — из констант, не из произвольных строк. Мутация инвалидирует **точечные** ключи, а не весь кэш.
- Типы контракта на клиенте описываются вручную и держатся в соответствии с zod-схемами сервера. Расхождение контракта — баг, который чинится в обеих частях одной задачей.

**Backend:**

- Один ресурс — один модуль в `modules/`. Ручки объявляются со схемами запроса и ответа.
- Ответ формирует контроллер, а не сервис. Сервис возвращает доменные данные или бросает доменную ошибку.

## 11. Состояние (frontend)

Библиотек глобального состояния (Redux/Zustand/Jotai) в проекте **нет** — не добавляй их без явного согласования. Порядок выбора:

1. **Серверный контент — на сервере.** Всё, что можно отрендерить в React Server Component, не должно попадать в клиентское состояние вовсе.
2. **Серверные данные на клиенте — TanStack Query.** Ответ не копируется в `useState`: кэш и есть источник правды.
3. **Локальное состояние — `useState`/`useReducer`** в ближайшем общем владельце.
4. **Состояние экрана — в URL** (`useSearchParams` + `router.replace`): фильтры, вкладки, активный раздел переживают перезагрузку и делятся ссылкой.
5. **React Context** — только для по-настоящему сквозного (тема). Контекст со всем подряд — источник лишних ререндеров.

`localStorage` используем точечно, через именованные константы ключей и всегда с проверкой на серверный рендер.

## 12. React и Next.js

- **Серверные компоненты по умолчанию.** `"use client"` добавляется только там, где нужны состояние, эффекты, браузерные API или обработчики событий, и ставится **как можно ниже по дереву** — на конкретный интерактивный компонент, а не на страницу целиком.
- **Компоненты — стрелочные функции с именованным экспортом.** `React.FC` не используем: типизируем пропсы напрямую (`({ a, b }: IProps) =>`). Исключение — `page.tsx`/`layout.tsx`, где Next требует `default export`.
- **Guard-clause приветствуется:** ранний `return null` / скелетон / пустое состояние в начале функции читается лучше, чем тройной тернарник в JSX. Вложенные тернарники глубже одного уровня запрещены.
- **Правила хуков соблюдаем строго:** только на верхнем уровне, честные зависимости, никаких условных вызовов. `useEffect` — для синхронизации с внешним миром, не для вычисления производных данных.
- **Один компонент — одна ответственность.** Компонент, который и грузит, и фильтрует, и рисует, — это два компонента и один хук.
- **Композиция вместо флагов.** Пять булевых пропсов, переключающих режимы, — сигнал, что нужны разные компоненты или `children`/слоты.
- **Списки — стабильный `key` из данных**, не индекс массива.
- **Навигация — `next/link`**, изображения — `next/image`, шрифты — `next/font`. Ручные `<a>` на внутренние маршруты и `<img>` для локальных изображений не используем.
- **Метаданные — через `metadata` / `generateMetadata`** в файлах роутов, не через ручные вставки в `<head>`.
- **React Compiler не включён** — `useMemo` / `useCallback` / `React.memo` расставляем вручную там, где это обосновано (§16).

## 13. UI и стилизация

- **Tailwind CSS 4 — основной инструмент стилизации.** Локальный `style.css` внутри модуля — для того, что классами выражается плохо (сложные селекторы, keyframes). Глобальное — только `shared/styles/globals.css`.
- **`!important` в Tailwind v4 — постфиксом:** `flex!`, `bg-red-500!`. Префиксная форма `!flex` не работает.
- **Inline `style={{}}`** допустим для **вычисляемых** значений (проценты, `transform`, цвет из данных). Статическое оформление — классами.
- **Дизайн-токены** (цвета, типографика, отступы бренда) объявляются один раз в теме Tailwind/CSS-переменных и используются по имени. Произвольные hex-значения в разметке — признак пропущенного токена.
- **Иконки** — `lucide-react`, импорт каждой иконки по имени. `import * as Icons` запрещён.
- **Анимации** — CSS-переходы либо `motion` (framer-motion); анимируем только `transform`/`opacity`, уважаем `prefers-reduced-motion`.
- **`cn()` из `@shared/lib`** — склейка классов на `clsx` + `tailwind-merge`, конфликты утилит разрешаются корректно.
- **Адаптивность — mobile-first**, flex/grid. Сайт в первую очередь смотрят с телефона.
- **Доступность** — семантические теги, один `<h1>` на страницу, корректная иерархия заголовков, `aria-label` на иконочных кнопках, видимый фокус, работа с клавиатуры, контраст ≥ 4.5:1.

## 14. UI-библиотеки: правило неприкосновенности

Проект строится на **Tailwind + собственных компонентах в `shared/ui`**. Тяжёлые UI-киты (Ant Design, MUI, Chakra, Mantine) для публичного сайта не используются: они раздувают бандл и навязывают чужой визуальный язык.

**Жёсткие правила:**

1. **Новые UI-зависимости не добавляем** без явного согласования.
2. Нужный компонент (кнопка, поле, модалка, аккордеон) сначала ищем в `shared/ui` и только потом заводим новый.
3. Если нужна сложная доступная механика (диалог, поповер, таб-панель) — берём headless-примитивы, а не полноценный кит, и только по согласованию.
4. Правишь существующий компонент — сохраняешь его текущий стиль и структуру.

## 15. Конфигурация и окружение

- В репозитории живут только `client/.env.example` и `server/.env.example`. Реальные `.env` в git не попадают никогда.
- Каждая новая переменная окружения одновременно: добавляется в соответствующий `.env.example` с комментарием, описывается в схеме валидации (`server/src/config`) и упоминается в `docs/ARCHITECTURE.md`, если влияет на архитектуру.
- Переменные клиента, доступные браузеру, обязаны иметь префикс `NEXT_PUBLIC_`. **Секреты префикса `NEXT_PUBLIC_` не получают никогда.**
- Приложение падает на старте с внятной ошибкой, если обязательная переменная не задана. Молчаливые дефолты для секретов запрещены.

## 16. Производительность по умолчанию

Перф-правила делятся на два класса, и путать их нельзя.

**Write-time — обязательны всегда, прямо здесь.** Стоят ноль при написании и дорого стоят при исправлении задним числом.

*Frontend:*

1. **Серверный рендер по умолчанию.** Компонент без интерактива не становится клиентским; `"use client"` — вниз по дереву, на минимальный узел.
2. **Тяжёлое — лениво.** Карты, слайдеры, видеоплееры, редакторы, крупные модалки — `next/dynamic` или динамический `import()` в момент действия. Никогда статическим импортом в always-mounted коде.
3. **Скрытое не монтируется.** Содержимое неактивной вкладки, закрытой модалки, свёрнутой панели не рендерится вовсе, а не прячется через `display: none`.
4. **Изображения — `next/image`** с заданными `width`/`height` (или `fill` + `aspect-ratio`), современным форматом и осмысленным `alt`. LCP-изображение — с `priority`, остальные — ленивые.
5. **Шрифты — `next/font`** с нужным подмножеством (`cyrillic`, `latin`) и `display: "swap"`; вариативное начертание вместо набора статических.
6. **Стабильные `key`** из данных, не индекс массива.
7. **Константные объекты и массивы — вне рендера** (константа модуля или `useMemo`).
8. **Никаких новых объектов, массивов и стрелок в пропсах мемоизированных или тяжёлых детей.**
9. **`React.memo` — тяжёлым детям** со стабильными пропсами. Лёгкие компоненты мемоизировать не нужно, это шум.
10. **Ввод, бьющий в API или тяжёлый рендер, — через debounce**; тяжёлая фильтрация — `useDeferredValue`.
11. **Анимации — только `transform` и `opacity`**, с уважением к `prefers-reduced-motion`.
12. **Никаких тяжёлых синхронных вычислений** в обработчиках и на рендере.
13. **`error.tsx` / `loading.tsx`** у крупных сегментов маршрута, `<Suspense>` вокруг асинхронных блоков.
14. **Вес новой зависимости проверяем до установки** — ESM и tree-shaking обязательны.

*Backend:*

1. **Ничего блокирующего в обработчике запроса.** Отправка письма, генерация файла, обращение к внешнему API не задерживают ответ — ставим в очередь или фоновую задачу.
2. **Подготовленные выражения SQLite создаются один раз** (на модуль), а не на каждый запрос.
3. **SQLite — в режиме WAL**, с индексами под реальные запросы и одним подключением на процесс.
4. **Транспорт Nodemailer создаётся один раз** (пул соединений), а не на каждое письмо.
5. **Кэш и `Cache-Control` на публичный контент** — ответы, которые меняются редко, не должны каждый раз собираться заново.
6. **Пагинация вместо «отдать всё»**; в списках не возвращаем тяжёлые поля.
7. **Логи структурные и без лишнего объёма** в горячем пути.

**Measure-time — по данным профайлера, не по интуиции.** Анализ бандла, разбиение чанков, виртуализация, Web Workers, preload/fetchpriority, `content-visibility`, бюджеты и Lighthouse на клиенте; профилирование запросов, план выполнения SQL, нагрузочные тесты на сервере. Свод и методика — **`PERFORMANCE.md`** (frontend) и **`server/PERFORMANCE.md`** (backend).

Правило совместного действия: `AGENTS.md` действует всегда; руководства по производительности авторитетны по вопросам скорости и применяются на выделенном перф-проходе или аудите. В перф-цикле приостанавливаются только §5 и §7 этого файла — переразбивать модули ради структуры там нельзя.

## 17. SEO и контент

Для публичного сайта это часть функциональности, а не «плюс к баллам»:

- Уникальные `title` и `description` на каждой странице через `generateMetadata`; Open Graph и Twitter-карточки для страниц, которыми делятся.
- `sitemap.ts` и `robots.ts` в `src/app/`, канонические URL, `lang="ru"` на `<html>`.
- Семантическая разметка и структурированные данные (JSON-LD: `Organization`, `LocalBusiness`, `BreadcrumbList`) там, где они уместны.
- Контент отдаётся сервером в HTML. Ключевой текст, который появляется только после клиентского запроса, для поиска не существует.
- Тексты — на русском, в деловом, но живом тоне; без канцелярита и без англицизмов там, где есть русское слово.

## 18. Загрузки, ошибки, пустые состояния

Каждый блок с данными обрабатывает все три состояния явно:

- **загрузка** — скелетон фиксированного размера (`loading.tsx` или `<Suspense>`), без «прыжков» layout;
- **ошибка** — понятное сообщение пользователю и возможность повтора (`error.tsx` сегмента); техническая причина — в лог, не в интерфейс;
- **пусто** — понятный текст и, если уместно, действие.

Пустой экран без объяснения — баг.

## 19. Комментарии и документация

- **Комментарий объясняет «почему», а не «что»**: ограничение внешней системы, неочевидное требование, причина обходного пути.
- **Не пишем**: пересказ кода, баннеры-разделители, TODO без контекста, авторские пометки, JSDoc ради JSDoc.
- **Закомментированный код удаляем.** История есть в git.
- Публичные хуки и нетривиальные утилиты в `shared` — короткий doc-комментарий с назначением.
- Существенные изменения проектируем дизайн-документом в `docs/plans/YYYY-MM-DD-<slug>-design.md`: проблема → изменения по файлам → верификация.
- Изменения архитектуры (новый слой, новый модуль backend, новая внешняя интеграция) отражаем в `docs/ARCHITECTURE.md` той же задачей.

## 20. Процесс и правила для AI-агентов

**Ветки и коммиты.** Работа идёт в ветках с PR в `main`. Сообщения коммитов — короткие, на русском, по существу («Добавил секцию услуг»), без служебного шума.

**Обязательные ограничения для агентов:**

0. **Не коммитить и не пушить по своей инициативе.** Изменения остаются в рабочем каталоге — их просматривает и отправляет пользователь. `git commit`, `git push`, создание PR — только по явной просьбе в текущей сессии; разрешение, данное один раз, не переносится на следующие шаги и сессии. Закончив работу, перечислить изменённые файлы.
1. **Не запускать прод-сборку (`npm run build`) и dev-сервер без явной просьбы.** При этом перед завершением любой задачи агент **ОБЯЗАН** выполнить быстрые статические проверки (`npm run typecheck` и `npm run lint` в соответствующей части или корне) и сразу исправить все найденные ошибки типов, линтинга, нарушения FSD-импортов и неиспользуемые переменные/логи.
2. **Не проводить браузерное/визуальное тестирование** и не запускать dev-сервер для проверки внешнего вида — пользователь тестирует визуал сам. Исключение — явная просьба.
3. **Не делать массовых рефакторингов** вне явно поставленной задачи.
4. **Не добавлять и не обновлять зависимости** без согласования. Новая зависимость — отдельное решение с обоснованием веса и лицензии.
5. **Не создавать код приложения раньше постановки задачи.** Пока задача — архитектура или конфигурация, страницы, компоненты, эндпоинты и схемы БД не пишутся.
6. **Перед правкой — прочитать соседние файлы** и следовать их стилю: этот документ описывает норму, а не оправдывает переписывание чужого кода под неё.
7. **Не смешивать части проекта в одной правке без нужды**: изменение контракта API — единственный законный повод трогать `client` и `server` одной задачей.
8. **Отчитываться честно:** что сделано, что не сделано и почему; не заявлять о проверке, которая не проводилась.

## 21. Definition of Done

- [ ] Frontend-код лежит в `client`, backend-код — в `server`; корень не засорён.
- [ ] Статические проверки пройдены: `npm run typecheck` и `npm run lint` завершаются без ошибок и предупреждений.
- [ ] Правило слоёв FSD не нарушено, импорты идут только вниз; в `shared` нет импортов из верхних слоёв (включая `import type`), общие типы вынесены в `@shared/types`.
- [ ] Новые файлы укладываются в ~250 строк; выросшее — декомпозировано осмысленно.
- [ ] Никаких хардкод-путей и адресов: только `ApiRoutes` / `AppRoutes` и конфигурация окружения.
- [ ] Нет `any`, нет неиспользуемых импортов, переменных и `console.log`; `strict` не обойдён.
- [ ] Серверный рендер по умолчанию; `"use client"` — только там, где нужен, и на минимальном узле.
- [ ] Обработаны загрузка, ошибка и пустое состояние.
- [ ] Write-time перф (§16) соблюдён: тяжёлое — лениво, скрытое не смонтировано, изображения и шрифты по правилам, `key` из данных.
- [ ] Метаданные страницы заданы; заголовки, `alt` и `aria-label` на месте.
- [ ] Для backend: вход валидирован, SQL параметризован, ошибки проходят через общий обработчик, секреты — из окружения.
- [ ] Нет закомментированного кода и комментариев-пересказов.
- [ ] Стиль соответствует соседним файлам; библиотека компонентов не подменена.
