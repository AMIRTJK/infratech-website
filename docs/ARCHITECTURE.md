# Архитектура проекта `infratech-website`

Документ описывает устройство репозитория: что и где лежит, как части взаимодействуют, чем настроены и какие правила производительности к какой части относятся.

**Статус:** подготовлена архитектура, структура директорий и конфигурация. Код приложения (страницы, компоненты, эндпоинты, схемы БД, бизнес-логика) **не написан** — это следующий этап.

Правила разработки — [`../AGENTS.md`](../AGENTS.md). Производительность: [`../PERFORMANCE.md`](../PERFORMANCE.md) (frontend) и [`../server/PERFORMANCE.md`](../server/PERFORMANCE.md) (backend). Разбор зависимостей — [`DEPENDENCIES.md`](DEPENDENCIES.md).

---

## 1. Что мы строим

Публичный информационный сайт организации: рассказ об организации, её деятельности, услугах, проектах, контактах; форма обратной связи с уведомлением на почту. Это **не** CRM и **не** внутренняя система — нет ролей, прав, реестров и рабочих процессов сотрудников.

Из этого следуют три архитектурных приоритета, определяющих все решения ниже:

1. **Скорость первой загрузки и SEO** — посетитель приходит из поиска, чаще всего с телефона. Контент должен приходить готовым HTML с сервера.
2. **Минимум клиентского JavaScript** — интерактива мало, платить за него бандлом незачем.
3. **Устойчивость публичного периметра** — API открыто интернету: валидация, лимиты и защита формы обязательны с первого дня.

## 2. Общая схема

```
┌──────────────────┐        HTTP / JSON, /api/v1/*        ┌──────────────────┐
│      client      │ ───────────────────────────────────▶ │      server      │
│  Next.js :3000   │ ◀─────────────────────────────────── │  Fastify :4000   │
│  React + TS      │        { success, message, data }    │  Node.js + TS    │
└──────────────────┘                                      └────────┬─────────┘
   ▲ браузер                                                       │
   │ HTML/RSC                                              ┌───────┴────────┐
   │                                                       │                │
посетитель                                          SQLite (файл)    SMTP (Nodemailer)
                                                    server/data/     письма с заявками
```

Две **независимые** программы: свои зависимости, своя конфигурация, свой `package.json`, свой процесс, свой терминал. Общего кода нет; единственная точка связи — HTTP-контракт.

**Почему не один Next-проект с Route Handlers.** Слитая архитектура даёт короткий старт и длинную расплату: серверная логика начинает жить внутри рендеринга, база и SMTP оказываются в том же процессе, что и отдача HTML, а масштабировать и перезапускать части раздельно уже нельзя. Разделение фиксирует границу с первого дня: фронтенд можно вынести на любой хостинг или CDN, бэкенд — обновлять и нагружать независимо.

### 3.1. `client/` — frontend

```
client/
├── package.json                 # зависимости и скрипты ТОЛЬКО фронтенда
├── tsconfig.json                # strict + псевдонимы слоёв FSD
├── next.config.ts               # режимы сборки, изображения, анализатор бандла
├── postcss.config.mjs           # подключение Tailwind CSS 4
├── eslint.config.mjs            # правила линта + запрет импортов вверх по слоям
├── .prettierrc.json
├── .env.example                 # адреса API и сайта (реальный .env.local — вне git)
├── README.md
├── public/                      # статика: изображения, favicon, og-картинки
└── src/
    ├── app/                     # МАРШРУТИЗАЦИЯ Next (App Router)
    │   └── _providers/          # клиентские провайдеры: QueryClient, тема, ErrorBoundary
    ├── views/                   # слой FSD «страницы» (имя pages занято Next)
    ├── widgets/                 # крупные блоки: шапка, футер, hero, секции
    ├── features/                # сценарии: форма обратной связи, поиск, переключатели
    ├── entities/                # доменные типы и представления: услуга, новость, проект
    └── shared/
        ├── api/                 # HTTP-клиент и реестр ApiRoutes
        ├── config/              # конфигурация окружения, AppRoutes, константы сайта
        ├── lib/                 # утилиты и хуки: cn, форматирование, debounce
        ├── ui/                  # базовые компоненты проекта: кнопка, поле, модалка
        ├── types/               # общие типы
        └── styles/              # globals.css и токены темы
```

**Назначение слоёв и правило импорта** — `app → views → widgets → features → entities → shared`, только вниз. Слой `pages` из канонического FSD переименован в `views`, потому что `src/app/` в Next занята роутером. Правило проверяется ESLint: попытка импортировать `@widgets/*` из `features/` падает на линте, а не на ревью.

Директория `app/_providers/` начинается с подчёркивания — Next считает такие папки приватными и не превращает их в маршруты.

### 3.2. `server/` — backend

```
server/
├── package.json                 # зависимости и скрипты ТОЛЬКО бэкенда
├── tsconfig.json                # strict, ESM (NodeNext), сборка в dist/
├── eslint.config.mjs            # правила линта + запрет SQL и nodemailer вне своих слоёв
├── .prettierrc.json
├── .env.example                 # порт, CORS, путь к SQLite, SMTP, лимиты
├── PERFORMANCE.md               # производительность BACKEND
├── README.md
├── data/                        # файл базы SQLite (в git не попадает)
├── tests/                       # тесты на встроенном раннере Node
└── src/
    ├── app/                     # бутстрап: main.ts, сборка сервера, graceful shutdown
    ├── config/                  # чтение и валидация переменных окружения
    ├── modules/                 # доменные модули API (по одному на ресурс)
    │   └── <module>/            # routes → controller → service → repository + schema
    ├── db/                      # подключение к SQLite, миграции, seed
    │   └── migrations/          # нумерованные SQL-миграции, только вперёд
    ├── mail/                    # транспорт Nodemailer и отправка писем
    │   └── templates/           # шаблоны писем
    ├── middlewares/             # общие плагины: ошибки, rate limit, CORS, логирование
    ├── shared/                  # утилиты, общие типы, доменные ошибки
    └── types/                   # общие типы и расширения типов Fastify
```

**Слои внутри модуля:** `routes` объявляет маршрут и схемы → `controller` разбирает запрос и формирует ответ → `service` содержит бизнес-логику и не знает о HTTP → `repository` работает с базой и является **единственным местом с SQL**. Обратные зависимости запрещены; часть ограничений проверяется линтом.

## 4. Размещение серверной логики, SQLite и Nodemailer

| Что | Где живёт | Правило |
|---|---|---|
| **Вся бизнес-логика** | `server/src/modules/*/​*.service.ts` | В `client` бизнес-логики нет. Route Handlers Next для неё не используются |
| **SQLite: файл базы** | `server/data/app.sqlite` (путь из `DATABASE_PATH`) | В git не попадает; в репозитории версионируются только миграции |
| **SQLite: подключение** | `server/src/db/` | Одно подключение на процесс, режим WAL, закрывается при остановке |
| **SQLite: схема** | `server/src/db/migrations/NNN_*.sql` | Только вперёд; применённая миграция не редактируется |
| **SQLite: запросы** | `server/src/modules/*/​*.repository.ts` | Единственное место с SQL, только подготовленные выражения с параметрами |
| **Nodemailer: транспорт** | `server/src/mail/` | Создаётся один раз при старте, с пулом соединений и таймаутами |
| **Nodemailer: шаблоны** | `server/src/mail/templates/` | Компилируются один раз |
| **Отправка письма** | `server/src/mail/` через фоновую задачу | Модули API не вызывают `nodemailer` напрямую и **не ждут** отправки в ответе |
| **Секреты (SMTP, пути)** | `.env` → `server/src/config/` | В коде и в git секретов нет |

**Сценарий формы обратной связи** (спроектирован, не реализован): клиент отправляет `POST /api/v1/contact-requests` → схема валидирует вход → сервис сохраняет обращение в SQLite (это источник правды) → клиент **сразу** получает ответ → письмо уходит фоном с ретраями. Пользователь не ждёт SMTP, а заявка не теряется, даже если почта временно недоступна.

## 5. Взаимодействие frontend и backend

**Контракт.** REST с версией: `/api/v1/<resource>`. Единый конверт ответа:

```ts
{ success: boolean; message: string; data: T }
```

Ошибки — тот же конверт с `success: false`, корректным HTTP-статусом и понятным сообщением на русском; детали валидации — в `data`.

**Адреса — только из конфигурации, никогда из кода:**

| Переменная | Где используется | Назначение |
|---|---|---|
| `NEXT_PUBLIC_API_URL` | `client`, браузер | Базовый адрес API для клиентских запросов; попадает в бандл, секретов не содержит |
| `API_INTERNAL_URL` | `client`, сервер Next | Адрес API для серверных компонентов; в продакшене может быть внутренним |
| `NEXT_PUBLIC_SITE_URL` | `client` | Публичный адрес сайта: канонические URL, sitemap, Open Graph |
| `CORS_ORIGINS` | `server` | Явный список разрешённых источников; `*` не используется |

**Кто и как запрашивает данные:**

- **Контент страниц — на сервере Next**: серверные компоненты и `views` ходят в API через `fetch` с осознанными `cache`/`revalidate`. Контент приходит в HTML — это и скорость, и индексация.
- **Интерактивные запросы — в браузере**: отправка формы, подгрузка «показать ещё», фильтры — через TanStack Query поверх общего HTTP-клиента из `shared/api`.
- **URL — только из `ApiRoutes`** (`client/src/shared/api/api-routes.ts`), маршруты страниц — только из `AppRoutes` (`client/src/shared/config/app-routes.ts`).

**Типы контракта не разделяются между частями.** На сервере они выводятся из zod-схем модуля, на клиенте описываются в `entities`. Это осознанное дублирование: общий пакет типов связал бы два независимых приложения и потребовал бы сборочной инфраструктуры ради нескольких интерфейсов. Расхождение контракта — баг, который чинится в обеих частях одной задачей.

## 6. Зависимости и команды запуска

У каждой части — **свой `package.json`** и своё дерево `node_modules`; workspaces не используются. Это и есть техническая гарантия независимости: `npm install` в `client` ничего не знает о `server`, и обновление зависимости одной части не может задеть другую.

Корневой `package.json` существует **только ради удобства запуска**: у него нет зависимостей приложения, есть единственная dev-зависимость `concurrently`, а все его скрипты — это вызовы скриптов `client` и `server` через `npm --prefix`. Он не объединяет части и не может стать местом для общего кода.

```bash
# один раз
npm install        # ставит зависимости корня, client и server (postinstall)

# обычный режим: обе части одной командой
npm run dev        # client :3000 и server :4000 в одном терминале, Ctrl+C останавливает оба
```

Каждая часть при этом остаётся самостоятельной — при работе над одной из них удобнее свой терминал, чтобы логи не перемешивались:

```bash
cd client && npm run dev     # http://localhost:3000
cd server && npm run dev     # http://localhost:4000
```

| Скрипт в корне | Что вызывает |
|---|---|
| `dev` | `client: next dev` + `server: tsx watch` через `concurrently -k` |
| `build` / `start` | Сборку и запуск прод-версий обеих частей |
| `typecheck` / `lint` / `format` | Соответствующие скрипты обеих частей |
| `test` | Тесты `server` (на клиенте тестового окружения нет) |
| `install:all` | `npm install` в `client` и `server`; вызывается автоматически из `postinstall` |

Остальные команды — в `client/README.md` и `server/README.md`.

## 8. Производительность: что где и что общее

Руководств два, потому что предметы разные: на клиенте оптимизируют байты и кадры, на сервере — миллисекунды и блокировки.

| Документ | Расположение | Область |
|---|---|---|
| **Frontend** | [`../PERFORMANCE.md`](../PERFORMANCE.md) (корень) | Всё, что касается `client` |
| **Backend** | [`../server/PERFORMANCE.md`](../server/PERFORMANCE.md) | Всё, что касается `server` |

**Только frontend:** стратегия рендеринга Next (SSG/ISR/SSR/CSR), граница серверных и клиентских компонентов, объём бандла и динамические импорты, ререндеры React и мемоизация, TanStack Query на клиенте, изображения (`next/image`) и шрифты (`next/font`), CSS и Tailwind, анимации, работа главного потока браузера, Core Web Vitals и Lighthouse, сторонние скрипты.

**Только backend:** задержка ответа и её хвосты (p95/p99), event loop и синхронные операции, SQLite (WAL, индексы, подготовленные выражения, транзакции, `EXPLAIN QUERY PLAN`), кэш ответов и заголовки, Nodemailer и фоновые задачи, лимиты и защита от перегрузки, логирование, graceful shutdown, масштабирование.

**Общее для обеих частей** (сформулировано в обоих документах применительно к своей стороне):

1. Сначала измерь, потом оптимизируй — правки без цифр «до/после» не принимаются.
2. Самая быстрая работа — та, которую не делают: не загруженный чанк, не выполненный запрос, не отправленный байт.
3. Кэшировать осознанно, с понятной инвалидацией.
4. Передавать только нужные данные: пагинация, никаких тяжёлых полей в списках.
5. Откладывать всё, что можно отложить: ленивая загрузка на клиенте, фоновые задачи на сервере.
6. Проверять вес и необходимость зависимости до установки.
7. Держать бюджеты и ловить регресс до продакшена.

**Стык двух зон — TTFB и кэш-заголовки.** Сервер отвечает за скорость ответа и корректный `Cache-Control`; клиент — за осознанные `revalidate`/`staleTime` и отсутствие повторных запросов за тем же самым. Регресс LCP разбирают обе стороны, начиная с вопроса «сколько занял ответ API».

Дополнительно: правила `AGENTS.md` §16 — это write-time-минимум, обязательный всегда при написании кода. Руководства по производительности подключаются целиком на выделенном перф-проходе и аудите.

## 9. Что сделано и что дальше

**Сделано на этом этапе:** архитектура, структура директорий обеих частей, разделение зависимостей и команд запуска, конфигурация (TypeScript, Next, Tailwind, ESLint с проверкой границ слоёв, Prettier, окружение), правила разработки `AGENTS.md`, указатели `CLAUDE.md`/`GEMINI.md`, два руководства по производительности, документация репозитория.

**Не сделано намеренно:** страницы, компоненты, стили, API-эндпоинты, схема базы и миграции, отправка писем, установка пакетов — всё это относится к разработке приложения и начинается по отдельной постановке задачи.

**Порядок следующего этапа** (предлагаемый):

1. Установить зависимости в обеих частях, зафиксировать `package-lock.json`.
2. `server`: конфигурация окружения → бутстрап Fastify → подключение SQLite и первая миграция → модуль обращений с формы → модуль почты с фоновой отправкой.
3. `client`: корневой layout, шрифты и токены темы → HTTP-клиент и `ApiRoutes`/`AppRoutes` → базовые компоненты `shared/ui` → страницы и секции контента → форма обратной связи.
4. Прогон Lighthouse и `autocannon` по готовым страницам и ручкам, фиксация базовых значений бюджетов.
