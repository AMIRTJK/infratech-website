# 🚀 Руководство по оптимизации производительности backend (`server`)

> Область действия — **только `server/`**: Node.js 22+ · TypeScript 5.9 · Fastify · SQLite (better-sqlite3) · Nodemailer.
> Производительность frontend — отдельный документ: [`../PERFORMANCE.md`](../PERFORMANCE.md).
> Базовые правила разработки живут в [`../AGENTS.md`](../AGENTS.md) и действуют всегда.

**Зачем это здесь.** Backend публичного сайта отдаёт немного данных, но делает это на глазах у поисковых роботов и посетителей: его время ответа целиком попадает в **TTFB** страницы, а TTFB — верхняя граница LCP. Медленная ручка `/api/v1/services` — это не «серверная деталь», а минус к метрике фронтенда, которую видит каждый посетитель. Второй мотив — устойчивость: сайт открыт всему интернету, и одна незащищённая тяжёлая ручка кладёт весь процесс.

---

## ⚠️ Рамки работ по оптимизации

- Перф-цикл на сервере — **только скорость и устойчивость**: время ответа, потребление памяти, работа с базой, фоновые задачи. Контракт API при этом **не меняется** — фронтенд не должен узнать об оптимизации.
- **Изменение контракта, схемы данных или формата ответа — отдельная задача** с правкой обеих частей проекта.
- **Не мигрируем библиотеки и не меняем СУБД** в рамках перф-задач. Переход с SQLite на другую базу — согласованное архитектурное решение, а не следствие одного медленного запроса.
- **Не делаем архитектурный рефакторинг** ради структуры: в перф-цикле приостановлены §5 и §7 `AGENTS.md`.
- Любая оптимизация подтверждается измерением «до/после». Без цифр правка не принимается.

## 1. Философия: чем измеряется быстрый backend

Три бюджета, как и на фронтенде, но другие:

| Бюджет | Что это | Чем управляем |
|---|---|---|
| **Задержка** | Время ответа на запрос, особенно p95/p99 | Запросы к базе, блокировки event loop, сериализация |
| **Пропускная способность** | Сколько запросов процесс держит без деградации | Кэш, стоимость одного запроса, отсутствие лишней работы |
| **Устойчивость** | Что происходит на пике и при отказе внешней системы | Таймауты, лимиты, rate limit, фоновые очереди, graceful shutdown |

**Правило №1:** сначала измерь. «Кажется, тормозит база» без плана запроса и цифр — не диагноз.

**Правило №2:** самая быстрая работа — та, которую не делают. Лучший запрос к базе — не выполненный (кэш). Лучший байт — не отправленный. Лучшая фоновая задача — не блокирующая ответ.

**Правило №3 (специфика Node):** процесс однопоточный. Любая синхронная операция на сотню миллисекунд — это простой **всех** соединений, а не только текущего.

## 2. Метрики и бюджеты

| Метрика | Что измеряет | 🟢 Цель | 🔴 Плохо |
|---|---|---|---|
| **TTFB API (p95)** | Время ответа ручки чтения контента | ≤ 50 мс | > 200 мс |
| **p99 задержки** | Хвост распределения | ≤ 200 мс | > 1 с |
| **Event loop delay (p99)** | Задержка цикла событий под нагрузкой | ≤ 20 мс | > 100 мс |
| **Один запрос к SQLite** | Индексированное чтение | ≤ 1 мс | > 10 мс |
| **RSS процесса в покое** | Память | ≤ 150 МБ | рост без плато |
| **Время старта** | От запуска до готовности принимать запросы | ≤ 1 с | > 5 с |

Дополнительно:

- **Ответ ручки чтения не должен выполнять больше одного–двух запросов к базе.** Три и больше — почти всегда N+1 или отсутствующий JOIN.
- **Размер JSON-ответа списка** — ≤ 50 КБ. Больше — значит, в списке лежит то, что нужно только на детальной странице.
- **Отправка письма не входит в бюджет ответа вообще**: она асинхронна (§8).

## 3. Как измерять

### 3.1. Нагрузочный замер ручки

```bash
npx autocannon -c 50 -d 20 http://localhost:4000/api/v1/services
```

Смотрим p95/p99 и requests/sec, а не среднее: среднее прячет хвост, а посетитель живёт именно в хвосте. Замер делаем на прод-сборке (`npm run build && npm run start`), а не на `tsx watch` — dev-режим медленнее и цифры бессмысленны.

### 3.2. Диагностика узкого места

```bash
npx clinic doctor -- node dist/app/main.js     # общая картина: CPU, event loop, GC
npx clinic flame -- node dist/app/main.js      # где именно горит CPU
node --cpu-prof dist/app/main.js               # профиль без внешних зависимостей
```

`clinic doctor` первым делом отвечает на главный вопрос: упираемся мы в CPU, в event loop или в ожидание внешней системы.

### 3.3. Задержка event loop в рантайме

Мониторим постоянно, а не только при разборе инцидента: `perf_hooks.monitorEventLoopDelay()` или встроенные метрики Fastify под `@fastify/under-pressure`. Рост p99 задержки — ранний сигнал, что появилась синхронная тяжёлая операция.

### 3.4. План выполнения запроса SQLite

```sql
EXPLAIN QUERY PLAN SELECT * FROM news WHERE is_published = 1 ORDER BY published_at DESC LIMIT 20;
```

`SCAN TABLE` в плане на растущей таблице = отсутствующий индекс. `USE TEMP B-TREE FOR ORDER BY` = сортировка в памяти вместо индекса. Оба случая — повод добавить индекс, а не «переписать запрос покрасивее».

### 3.5. Время обработки запроса в логах

`pino` (встроенный логгер Fastify) уже пишет длительность ответа. Логируйте медленные запросы отдельным уровнем и держите порог (например, 100 мс) — так регресс виден без специального прогона.

## 4. Event loop — главный ресурс процесса

Всё в одном потоке. Один блокирующий вызов останавливает обслуживание всех клиентов.

**Чего не делать в обработчике запроса:**

- Синхронные операции с файлами (`readFileSync`, `writeFileSync`) — кроме старта приложения.
- Разбор или генерацию больших структур (мегабайтный JSON, CSV, PDF, изображения).
- Криптографию с высокой стоимостью (`bcrypt`, `pbkdf2` с большим числом итераций) в синхронном виде.
- Циклы по десяткам тысяч элементов.
- Ожидание внешней системы (SMTP, сторонний API) без таймаута.

**Что делать вместо:**

- **Тяжёлое — в `worker_threads`** или в фоновую задачу вне обработки запроса.
- **Внешние вызовы — с таймаутом и лимитом попыток.** Внешний сервис, отвечающий 30 секунд, не должен держать соединение посетителя.
- **Длинные циклы — чанками** с уступкой потоку (`await setImmediate()`), если вынести в поток нельзя.
- **Потоки вместо буферов**: файл отдаём стримом, а не читаем целиком в память.

> **Важно про `better-sqlite3`: он синхронный.** Это осознанный выбор — для наших объёмов индексированное чтение занимает десятки микросекунд и обходится дешевле, чем накладные расходы асинхронного драйвера. Но правило обратное по силе: **любой запрос к SQLite блокирует весь процесс на время выполнения.** Отсюда следует то, что в других базах опционально, а здесь обязательно: индексы под каждый реальный запрос, `LIMIT` во всех выборках, короткие транзакции, никакого экспорта «всей таблицы» в обработчике запроса. Массовые операции (импорт, миграция данных, отчёт) выполняются в отдельном скрипте или worker-потоке, а не в ручке API.

## 5. HTTP-слой и Fastify

### 5.1. Схема ответа — это не только валидация, но и скорость

Fastify по схеме ответа компилирует быстрый сериализатор (`fast-json-stringify`), который в разы быстрее `JSON.stringify` и заодно гарантирует, что наружу не утечёт лишнее поле.

```ts
// Схема ответа обязательна для каждой ручки: и контракт, и производительность
fastify.get("/api/v1/services", { schema: { response: { 200: servicesResponseSchema } } }, handler);
```

### 5.2. Валидация входа — на границе

Схема на `body`/`query`/`params` отсекает мусорный запрос до того, как он дойдёт до сервиса и базы. Отклонить невалидный запрос за 0.1 мс дешевле, чем выполнить по нему запрос к базе.

### 5.3. Сжатие — с умом

Сжимать ответы имеет смысл от ~1 КБ; на мелких ответах CPU-стоимость больше выигрыша. Статику (изображения, шрифты) не сжимаем повторно. В продакшене сжатие лучше отдать обратному прокси (nginx/CDN) — это снимает работу с Node-процесса.

### 5.4. Keep-alive и таймауты

Держите `keepAliveTimeout` согласованным с прокси (значение на сервере должно быть больше, чем у прокси, иначе ловим гонки и 502). Задайте `requestTimeout` и лимит тела (`bodyLimit`) — по умолчанию 1 МБ более чем достаточно для формы обратной связи.

### 5.5. Плагины — по стоимости

Каждый глобальный хук выполняется на каждом запросе. Плагин, нужный одному маршруту, регистрируется в области этого маршрута, а не глобально. Обработка ошибок, request-id и логирование — глобально, всё остальное — точечно.

### 5.6. Статику отдаёт не Node

Изображения, документы и загруженные файлы в продакшене отдаёт nginx или CDN. `@fastify/static` — для разработки и для файлов, требующих проверки прав.

## 6. SQLite: главный источник и главный риск

SQLite для сайта организации — правильный выбор: ноль сетевых задержек, ноль отдельного сервиса, чтение быстрее любой клиент-серверной базы. Взамен он требует дисциплины.

### 6.1. PRAGMA при открытии соединения

```ts
db.pragma("journal_mode = WAL");    // читатели не блокируют писателя — обязательно
db.pragma("synchronous = NORMAL");  // разумный компромисс надёжности и скорости при WAL
db.pragma("foreign_keys = ON");     // целостность
db.pragma("busy_timeout = 5000");   // ждать освобождения блокировки, а не падать
```

Без WAL любая запись (отправленная форма) блокирует чтение — то есть посетитель, заполнивший форму, тормозит всех остальных.

### 6.2. Одно подключение на процесс

Пул соединений SQLite не нужен и вреден. Подключение открывается один раз в `db/`, живёт весь процесс и закрывается при graceful shutdown.

### 6.3. Подготовленные выражения создаются один раз

```ts
// Плохо: компиляция SQL на каждый запрос
const findAll = () => db.prepare("SELECT * FROM services WHERE is_active = 1").all();

// Хорошо: подготовили один раз на уровне модуля, вызываем много раз
const selectActiveServices = db.prepare("SELECT id, title, slug FROM services WHERE is_active = 1");
const findAll = () => selectActiveServices.all();
```

Это же требование безопасности: параметры передаются связыванием, а не конкатенацией строк.

### 6.4. Индексы под реальные запросы

Индексируем то, по чему фильтруем и сортируем: `WHERE is_published`, `ORDER BY published_at`, `WHERE slug = ?`. Составной индекс должен идти в порядке использования колонок. Проверяем результат через `EXPLAIN QUERY PLAN` — не «на глаз».

Не индексируем всё подряд: каждый индекс замедляет вставку и занимает место.

### 6.5. Транзакции — для пакетов, и они короткие

```ts
const insertMany = db.transaction((rows) => { for (const row of rows) insertOne.run(row); });
```

Сто вставок в одной транзакции — один `fsync` вместо ста. Но транзакция держит блокировку записи и блокирует поток: держите её короткой, никакой сети и внешних вызовов внутри.

### 6.6. Никаких `SELECT *` и N+1

Перечисляем нужные колонки; список услуг не тянет большие текстовые поля описания. Данные связанных сущностей получаем одним запросом с `JOIN` или одним `WHERE id IN (...)`, а не запросом в цикле.

### 6.7. Всегда `LIMIT`

Любая выборка списка ограничена сверху — даже там, где «строк всего двадцать». Таблицы растут, а ручка без лимита однажды вернёт всё.

### 6.8. Обслуживание

`ANALYZE` после существенных изменений структуры, периодический `VACUUM` (в окно обслуживания, не в рантайме), контроль размера WAL-файла. Резервная копия — через `db.backup()`, а не копированием файла на живой базе.

## 7. Кэширование

Контент сайта меняется редко, читается часто — это идеальный профиль для кэша.

**Три уровня, по возрастанию стоимости:**

1. **HTTP-кэш на ответе.** Публичный контент отдаём с `Cache-Control: public, max-age=…, stale-while-revalidate=…` и `ETag`. Тогда повторный запрос завершается ответом `304` без работы с базой. Это самый дешёвый кэш: работу берут на себя браузер, CDN и Next.
2. **Кэш в памяти процесса.** Справочники, меню, редко меняющиеся списки держим в простой `Map` или LRU с TTL. Инвалидация — по событию изменения данных, а не только по времени. Ограничивайте размер: неограниченный кэш — это утечка памяти с отложенным сроком.
3. **Материализация в базе.** Тяжёлые агрегаты считаем заранее и храним готовыми, а не пересчитываем на каждый запрос.

**Чего не делать:** не кэшируйте персональные ответы под общим ключом и не ставьте `Cache-Control: public` на что-либо, зависящее от заголовков запроса. Ошибка в ключе кэша — это выдача чужих данных, а не просто промах.

## 8. Nodemailer и фоновые задачи

Отправка письма — обращение к внешней системе с непредсказуемой задержкой (SMTP спокойно отвечает секундами). **Ответ пользователю не ждёт письма.**

**Плохо:**

```ts
await mailer.sendMail(message);        // посетитель смотрит на спиннер 3 секунды
return reply.send({ success: true, message: "Заявка отправлена", data: null });
```

**Хорошо:** сначала сохранить обращение в базу (это и есть источник правды), сразу ответить пользователю, а письмо отправить фоном с ретраями:

```ts
const request = contactService.save(input);   // быстрый и надёжный шаг
mailQueue.enqueue({ kind: "contact", id: request.id });  // фон
return reply.send({ success: true, message: "Заявка принята", data: { id: request.id } });
```

**Правила модуля `mail/`:**

- **Транспорт создаётся один раз** при старте, с пулом соединений (`pool: true`, `maxConnections`, `maxMessages`): TLS-рукопожатие на каждое письмо — самая дорогая часть отправки.
- **Таймауты обязательны** (`connectionTimeout`, `greetingTimeout`, `socketTimeout`): зависший SMTP не должен копить соединения.
- **Ретраи с экспоненциальной задержкой и потолком попыток.** Бесконечный ретрай на недоступном SMTP — это бесконечный рост очереди.
- **Очередь ограничена по длине** и переживает перезапуск (при SQLite это таблица `mail_outbox` со статусом), иначе при падении процесса заявки теряются.
- **Массовые рассылки — не через ручку API.** Отдельный скрипт, свой темп, без влияния на веб-процесс.
- **Шаблоны компилируются один раз**, а не собираются строками на каждое письмо.
- **Вложения — стримом**, не буфером в памяти.

Тот же подход — к любой фоновой работе: генерация файла, обращение к внешнему API, вебхук. Обработчик запроса регистрирует задачу, а не выполняет её.

## 9. Данные, сериализация и пагинация

- **Пагинация обязательна** для любого списка: `limit` + `offset` или курсор. Курсор предпочтительнее при росте данных: `OFFSET` на больших смещениях заставляет базу пропускать строки одну за одной.
- **Список и деталь — разные наборы полей.** В списке — то, что видно в карточке; тяжёлые тексты и вложения — только в детальной ручке.
- **Формат ответа — единый конверт `{ success, message, data }`** (см. `AGENTS.md` §10) со схемой ответа, дающей быстрый сериализатор.
- **Даты — в ISO 8601 UTC**, форматирование — задача клиента. Локализация дат на сервере — это лишняя работа на каждый элемент списка.
- **Не отдавайте вычислимое.** Если поле выводится из другого, пусть его считает клиент — байты по сети дороже.
- **Большие ответы — стримом** (`NDJSON`/поток), а не одной строкой в памяти. Хотя на контентном сайте появление такой ручки — сам по себе повод для вопроса.

## 10. Логирование

- **Только структурный логгер** (`pino`, встроен в Fastify). `console.log` в горячем пути синхронен для файлового дескриптора и стоит дороже, чем кажется.
- **Уровни осознанные:** `info` — события уровня запроса, `debug` — только в разработке. Логирование тела каждого запроса на проде — это и утечка персональных данных, и заметная нагрузка.
- **Никакого `JSON.stringify` больших объектов ради лога.** Логируйте идентификаторы, а не сущности.
- **Request-id сквозной** — от входа до фоновой задачи: без него разбор инцидента превращается в гадание.
- Секреты, пароли, содержимое писем в логи не попадают никогда.

## 11. Управление ресурсами и жизненный цикл процесса

- **Graceful shutdown обязателен:** по `SIGTERM`/`SIGINT` перестаём принимать новые соединения, даём дожить текущим запросам (с потолком по времени), дописываем очередь, закрываем базу и SMTP-транспорт. Резкое падение при незакрытой SQLite — риск для WAL и потерянные письма.
- **Всё внешнее — с таймаутом.** Запрос без таймаута — это утечка соединения, ожидающая своего часа.
- **Ограничивайте параллелизм фоновых задач** (например, не больше 2–3 писем одновременно). «Отправим всё сразу» упирается в лимиты SMTP-провайдера и память.
- **Следите за памятью:** RSS должен выходить на плато. Постоянный рост — обычно неограниченный кэш, накапливающийся массив или незакрытый стрим. Проверяется снимком кучи (`--heapsnapshot-signal`).
- **Ничего тяжёлого на старте** сверх необходимого: миграции, подготовка выражений, создание транспорта — быстрые операции; долгий старт мешает перезапускам и деплою.
- **Проверка живости** (`/health`) — дешёвая ручка без обращения к внешним системам; отдельная `/ready` может проверять базу.

## 12. Защита как производительность

Для публичного API это одна и та же тема: незащищённая ручка деградирует не от нагрузки посетителей, а от одного скрипта.

- **Rate limit** на все публичные ручки, особенно на форму обратной связи (`@fastify/rate-limit`): лимит по IP и отдельный, более строгий — на отправку.
- **Лимит размера тела** запроса и количества полей — до разбора, а не после.
- **Валидация до работы:** отклонённый по схеме запрос не должен стоить ни одного обращения к базе.
- **CORS с явным списком источников** — не `*`.
- **Honeypot/капча на форме** дешевле, чем разбор спама и рассылка мусорных писем.
- **Ошибки не раскрывают внутренности:** стек и SQL — в лог, наружу — код и понятное сообщение.
- **Помните про DoS через регулярные выражения**: сложные regexp на пользовательском вводе выполняются в том же единственном потоке.

## 13. Масштабирование

Порядок действий — от дешёвого к дорогому, и первые три шага почти всегда закрывают вопрос для сайта организации:

1. **Кэш и HTTP-заголовки.** Запрос, не дошедший до Node, стоит ноль.
2. **Обратный прокси/CDN перед приложением**: TLS, сжатие, статика, кэш ответов — всё это снимается с процесса.
3. **Профилирование и устранение узкого места.** Один отсутствующий индекс часто стоит больше, чем весь горизонтальный масштаб.
4. **Вертикальный рост** (быстрее диск и CPU). SQLite очень выигрывает от быстрого диска.
5. **Несколько процессов (`cluster`/PM2) — с оговоркой про SQLite.** Читающие процессы в режиме WAL сосуществуют нормально, запись сериализуется блокировкой файла. Если процессов будет несколько, **писать должен один** (например, фоновый обработчик очереди), а веб-процессы — читать. Без этого получим `SQLITE_BUSY` под нагрузкой.
6. **Смена базы** — только когда измерения показали, что упёрлись именно в SQLite, и это отдельная согласованная задача.

**Что нужно заложить сразу, чтобы шаг 5 был возможен:** процесс не хранит состояние в памяти как источник правды (кэш — только производный и восстановимый), фоновые задачи идемпотентны и лежат в базе, а не в переменной, путь к базе и все настройки приходят из окружения.

## 14. Обязательные правила для новых эндпоинтов

Соблюдать при разработке **каждой** ручки — это write-time-правила, они действуют и вне перф-цикла:

1. **Схема на вход и на ответ.** Валидация отсекает мусор, схема ответа даёт быстрый сериализатор.
2. **Ничего блокирующего в обработчике.** Письма, файлы, внешние вызовы — в фон.
3. **Подготовленные выражения на уровне модуля**, не внутри функции-обработчика.
4. **Каждый запрос к базе покрыт индексом**, план проверен через `EXPLAIN QUERY PLAN`.
5. **`LIMIT` и пагинация** в любой выборке списка.
6. **Только нужные колонки**, никаких `SELECT *`, никакого N+1.
7. **Кэш-заголовки** для публичного контента; при необходимости — кэш в памяти с ограниченным размером и понятной инвалидацией.
8. **Rate limit и лимит тела** для публичной ручки.
9. **Таймаут на любое обращение вовне.**
10. **Ошибки — через общий обработчик**; наружу не уходят детали, в лог не уходят секреты.
11. **Логи структурные и экономные** в горячем пути.
12. **Транзакции короткие**, без сети внутри.
13. **Ответ не содержит вычислимого и лишнего** — вес JSON тоже бюджет.
14. **Вес и необходимость новой зависимости проверены** до установки.

### Общее с frontend и разделение зон

- **Общие принципы:** сначала измерять, потом оптимизировать; не делать лишней работы; кэшировать осознанно; ограничивать объём передаваемых данных; лениво выполнять всё, что можно отложить; следить за весом зависимостей; фиксировать бюджеты и ловить регресс до продакшена.
- **Зона frontend** (`../PERFORMANCE.md`): объём бандла, границы серверных и клиентских компонентов, ререндеры React, изображения, шрифты, CSS, анимации, Core Web Vitals, Lighthouse.
- **Зона backend** (этот документ): время ответа и его хвосты, event loop, SQLite и индексы, кэш ответов, Nodemailer и фоновые задачи, лимиты, устойчивость, масштабирование.
- **Стык двух зон:** TTFB и кэш-заголовки. Сервер отвечает за скорость ответа и корректный `Cache-Control`; клиент — за осознанные `revalidate`, `staleTime` и за то, чтобы не запрашивать одно и то же дважды. Регресс LCP на публичной странице разбирают обе стороны вместе, начиная с вопроса «сколько занял ответ API».
