# 🚀 Руководство по оптимизации производительности frontend (`client`)

> Область действия — **только `client/`**: Next.js 15 (App Router) · React 19 · TypeScript 5.9 · Tailwind CSS 4 · TanStack Query v5.
> Производительность backend — отдельный документ: [`server/PERFORMANCE.md`](server/PERFORMANCE.md).
> Базовые правила разработки (архитектура, именование, типизация, API, декомпозиция) живут в [`AGENTS.md`](AGENTS.md) и действуют всегда.

**Почему это критично именно здесь.** Проект — публичный сайт организации. Посетитель приходит из поиска или по ссылке, часто с телефона и слабой сети, и уходит, если страница «думает». Скорость здесь напрямую влияет на то, дочитает ли человек про организацию и отправит ли заявку, и на позиции в поиске. Для внутренней системы медленный экран — раздражение; для публичного сайта — потерянный посетитель.

---

## ⚠️ Рамки работ по оптимизации

Перф-цикл — **только производительность/скорость**. Границы:

- **Не меняем дизайн, вёрстку и расположение UI.** Внешний вид остаётся прежним; правки — «под капотом» (загрузка, рендеры, кэш, ресурсы). Если оптимизация неизбежно затрагивает внешний вид — останавливаемся и спрашиваем.
- **Не мигрируем библиотеки** в рамках перф-задач.
- **Не делаем архитектурный рефакторинг** (переразбиение по слоям, лимит ~250 строк) — в перф-цикле приостановлены §5 и §7 `AGENTS.md`.
- Рекомендации по **Accessibility/SEO (§16)** внедряем в части, не меняющей внешний вид (сжатие, кэш, размеры ресурсов, `alt`/`aria-label`, метаданные); визуальные правки — по отдельному запросу.

## 1. Философия: на что мы реально оптимизируем

Производительность — это **три отдельных бюджета**, которые нужно держать одновременно:

| Бюджет | Что это | Чем управляем |
|---|---|---|
| **Загрузка** | Сколько байт и запросов до первого полезного экрана | Объём бандла, разделение кода, сжатие, ресурсы |
| **Отзывчивость** | Задержка на клик/ввод (INP) | Работа главного потока, ререндеры, тяжёлые задачи |
| **Стабильность** | Ничего не «прыгает» (CLS) | Размеры-заглушки, шрифты, изображения, скелетоны |

**Правило №1:** сначала измерь, потом оптимизируй. Не оптимизируй то, что не подтверждено профайлером.

**Правило №2:** самая быстрая работа — та, которую не делают. Лучший чанк — не загруженный. Лучший ререндер — не случившийся. Лучший запрос — отданный из кэша. Лучший клиентский компонент — оставшийся серверным.

## 2. Метрики и бюджеты

### Core Web Vitals (цели)

| Метрика | Что измеряет | 🟢 Хорошо | 🔴 Плохо |
|---|---|---|---|
| **LCP** (Largest Contentful Paint) | Когда виден главный контент | ≤ 2.5 с | > 4.0 с |
| **INP** (Interaction to Next Paint) | Отзывчивость на ввод | ≤ 200 мс | > 500 мс |
| **CLS** (Cumulative Layout Shift) | Визуальная стабильность | ≤ 0.1 | > 0.25 |
| **TTFB** (Time To First Byte) | Ответ сервера | ≤ 0.8 с | > 1.8 с |
| **FCP** (First Contentful Paint) | Первый рендер | ≤ 1.8 с | > 3.0 с |

> Для публичного сайта **LCP и CLS — главные**: их видит каждый первый посетитель. LCP почти всегда — hero-изображение или заголовок первого экрана.

### Бюджеты (ориентир для этого проекта)

- **Initial JS (First Load JS главной страницы), gzip:** ≤ **120 КБ**. Лендинг с малым интерактивом не имеет права весить как дашборд.
- **Любой отдельный route-чанк, gzip:** ≤ **100 КБ**.
- **CSS initial, gzip:** ≤ **30 КБ**.
- **Hero-изображение:** ≤ **200 КБ** в AVIF/WebP на десктопном разрешении.
- **Тяжёлые виджеты (карта, плеер, слайдер, аналитика) — 0 КБ в initial.** Только по требованию.

Next выводит размер First Load JS по каждому маршруту прямо в выводе `npm run build` — это первый и самый дешёвый индикатор регресса.

## 3. Как измерять

### 3.1. Анализ бандла

```bash
cd client
npm run analyze     # next build с @next/bundle-analyzer
```

Смотрим treemap: что реально попало в бандл, какие библиотеки дублируются, что случайно затянуто в клиентский граф. Частая находка на публичном сайте — библиотека, попавшая в клиент из-за одного `"use client"` слишком высоко по дереву.

### 3.2. Реальные метрики пользователей (RUM)

Next даёт встроенный хук — внешняя библиотека `web-vitals` не нужна:

```ts
// client/src/app/_providers/WebVitals.tsx — "use client"
import { useReportWebVitals } from "next/web-vitals";

useReportWebVitals((metric) => {
  navigator.sendBeacon?.("/api/v1/metrics/vitals", JSON.stringify(metric));
});
```

Lighthouse — лабораторные условия. **RUM показывает правду о реальных посетителях** (их сеть, их устройства).

### 3.3. Lighthouse

Прогоняем по ключевым публичным страницам (главная, услуги, контакты) в режиме «Mobile» и «Slow 4G». Для публичного сайта цель — 90+ по Performance и 100 по Accessibility/Best Practices/SEO. Порог фиксируем в CI (`@lhci/cli`), чтобы регресс падал так же, как падают типы.

### 3.4. React DevTools Profiler

Вкладка **Profiler** → «Record» → выполнить сценарий → посмотреть, какие компоненты ререндерятся и почему. Включённое «Highlight updates when components render» показывает лишние перерисовки визуально.

### 3.5. Chrome DevTools → Performance и Coverage

- **Main thread** — ищем длинные задачи (> 50 мс), они убивают INP.
- **Coverage** (Ctrl+Shift+P → «Coverage») — сколько JS/CSS загружено, но не использовано.

## 4. Стратегия рендеринга Next.js

Это самый крупный рычаг: он определяет, сколько работы вообще достанется браузеру.

### 4.1. Выбор режима по типу страницы

| Тип контента | Режим | Как |
|---|---|---|
| Статические страницы (о нас, услуги, контакты) | **SSG** | По умолчанию: страница без динамических API рендерится на сборке |
| Контент из базы, меняющийся редко (новости, проекты) | **ISR** | `fetch(url, { next: { revalidate: 600 } })` или `export const revalidate = 600` |
| Персональное/частое | **SSR** | `cache: "no-store"` — только там, где это действительно нужно |
| Интерактив без SEO-ценности | **CSR** | Клиентский компонент + TanStack Query |

**Правило:** динамический рендер — осознанное решение, а не побочный эффект. Обращение к `cookies()`, `headers()` или `searchParams` переводит сегмент в динамику целиком — не тяните их выше, чем нужно.

### 4.2. Серверные компоненты по умолчанию

Каждый компонент, ставший клиентским, тащит в браузер себя и всё, что импортирует. `"use client"` на странице делает клиентским всё её поддерево.

**Плохо** — директива на уровне экрана ради одной кнопки:

```tsx
"use client";            // весь экран уехал в браузер
export const ServicesPage = () => { /* контент + одна интерактивная кнопка */ };
```

**Хорошо** — граница клиента на минимальном узле:

```tsx
// ServicesPage.tsx — серверный компонент, контент рендерится в HTML
export const ServicesPage = () => (
  <section>
    <ServicesList items={items} />
    <ContactButton />       {/* только этот файл начинается с "use client" */}
  </section>
);
```

### 4.3. `<Suspense>` и потоковая отдача

Медленный блок не должен задерживать всю страницу: оборачиваем его в `<Suspense>` со скелетоном фиксированного размера — остальная страница отдаётся сразу.

### 4.4. Не тащите серверные данные в клиент целиком

Пропсы клиентского компонента сериализуются в HTML (RSC payload) и увеличивают вес документа. Передавайте вниз ровно те поля, которые нужны для интерактива, а не весь ответ API.

## 5. Code splitting и границы клиента

### 5.1. Тяжёлое — только по требованию

Карты, слайдеры, плееры, редакторы, галереи с зумом, генерация файлов — это сотни килобайт. Их нельзя импортировать статически в always-mounted коде.

**Плохо:**

```tsx
import { MapView } from "@widgets/MapView"; // карта в бандле каждой страницы с футером
```

**Хорошо** — `next/dynamic` с отключённым SSR там, где компонент завязан на браузер:

```tsx
const MapView = dynamic(() => import("@widgets/MapView").then((m) => m.MapView), {
  ssr: false,
  loading: () => <MapSkeleton />,   // скелетон точного размера — нет CLS
});
```

**Хорошо** — динамический `import()` в момент действия:

```tsx
const handleShare = async () => {
  const { buildShareCard } = await import("@shared/lib/share-card");
  // ...
};
```

### 5.2. Скрытое не монтируется

Содержимое закрытой модалки, неактивной вкладки, свёрнутого аккордеона не рендерится вовсе, а не прячется через `display: none`. Спрятанный DOM всё равно стоит layout, памяти и рендера.

### 5.3. Prefetch — маскируем задержку

`next/link` префетчит маршруты в вьюпорте автоматически — не отключайте это без причины. Для тяжёлого компонента, открывающегося по клику, прогревайте чанк на `onMouseEnter`/`onFocus`: к моменту клика он уже в кэше.

### 5.4. Барели и точечные импорты

- `import * as Icons from "lucide-react"` затянет весь набор — импортируйте каждую иконку по имени.
- В `index.ts` модулей реэкспортируйте только нужное: барель «всё из всего» ломает tree-shaking и раздувает граф.
- Не добавляйте побочные эффекты на верхнем уровне модулей — их нельзя выкинуть при шейкинге.

## 6. Рендеринг React

**React Compiler в проекте не подключён** — мемоизация ручная, точечная и обоснованная. Лишние `useMemo`/`useCallback` тоже стоят памяти и времени сравнения.

### 6.1. `React.memo` и стабильные пропсы

```tsx
// Плохо: тяжёлая карточка перерисовывается при любом ререндере родителя
const ProjectCard = ({ project, onOpen }: IProps) => { /* сложный JSX */ };

// Хорошо: memo + стабильный колбэк
const ProjectCard = memo(({ project, onOpen }: IProps) => { /* сложный JSX */ });
const onOpen = useCallback((id: string) => setActive(id), []);
```

`memo` без стабильных пропсов бесполезен: новый объект или стрелка в пропсах ломает сравнение.

### 6.2. `useMemo` — для дорогого, не для примитивов

```tsx
// Плохо: оверхед больше пользы
const title = useMemo(() => `${first} ${last}`, [first, last]);

// Хорошо: реально дорогое вычисление
const sorted = useMemo(() => [...items].sort(byDate), [items]);
```

### 6.3. Не создавайте объекты, массивы и функции в JSX-пропсах

```tsx
// Плохо
<Gallery config={{ mode: "grid" }} items={photos.filter((p) => p.isPublic)} />

// Хорошо
const GRID_CONFIG = { mode: "grid" } as const;
const publicPhotos = useMemo(() => photos.filter((p) => p.isPublic), [photos]);
<Gallery config={GRID_CONFIG} items={publicPhotos} />
```

### 6.4. Стабильные `key`

`key={index}` при вставке, удалении или сортировке путает React: теряется состояние, растут перерисовки. Ключ — идентификатор из данных.

### 6.5. Контекст — дробный, состояние — локальное

Один «god-context» перерисовывает всех потребителей на любое изменение. Дробите по частоте изменения (тема отдельно, редкое отдельно), держите состояние как можно ближе к месту использования.

### 6.6. `useTransition` и `useDeferredValue`

Ввод в поиск, перестраивающий большой список, лагает, потому что рендер блокирует отрисовку ввода:

```tsx
const [query, setQuery] = useState("");
const deferredQuery = useDeferredValue(query);
const filtered = useMemo(() => filterItems(items, deferredQuery), [items, deferredQuery]);
```

Для переключения тяжёлых вкладок — `startTransition`: UI остаётся отзывчивым, старый контент виден, пока готовится новый.

### 6.7. Формы

Контролируемый инпут вызывает ререндер на каждое нажатие. Для формы обратной связи достаточно неконтролируемых полей с `ref` (или `useActionState` из React 19) — состояние на каждый символ не нужно. Не поднимайте состояние поля выше, чем требуется.

### 6.8. Возможности React 19, которые экономят код и рендеры

- **`ref` как обычный проп** — `forwardRef` больше не нужен.
- **Document Metadata** — метаданные рендерятся из компонентов; в App Router предпочитаем `generateMetadata`.
- **Actions / `useActionState` / `useOptimistic`** — отправка формы и оптимистичные обновления без ручного бойлерплейта.

## 7. Данные и TanStack Query

На публичном сайте большая часть данных приходит на сервере (§4). TanStack Query нужен там, где данные запрашивает **браузер**: отправка формы, ленивая подгрузка списка, фильтры без перезагрузки.

### 7.1. Осознанные `staleTime` и `gcTime`

`staleTime: 0` (значение по умолчанию) означает, что любые данные устаревают мгновенно → повторный запрос на каждый маунт и возврат фокуса.

```ts
export const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      retry: 1,
      staleTime: 60_000,           // 1 мин: не дёргаем сервер зря
      gcTime: 5 * 60_000,          // держим в памяти для мгновенного возврата
      refetchOnWindowFocus: false, // на контентном сайте фокус-рефетчи только мешают
      refetchOnReconnect: true,
    },
  },
});
```

Тонкая настройка — по типу данных: справочники и разделы контента → минуты и часы; списки, меняющиеся часто → десятки секунд.

### 7.2. `select` — не тащить лишнее в компонент

```tsx
// Плохо: компонент подписан на весь ответ
const { data } = useQuery({ queryKey: NEWS_KEY, queryFn: fetchNews });
const count = data?.items.length;

// Хорошо: подписка только на число
const { data: count } = useQuery({
  queryKey: NEWS_KEY,
  queryFn: fetchNews,
  select: (res) => res.items.length,
});
```

### 7.3. Пагинация без «схлопывания»

При смене страницы или фильтра держим прошлые данные, пока грузятся новые: `placeholderData: keepPreviousData` (v5). Пустой экран со спиннером между страницами — это и мелькание, и лишний CLS.

### 7.4. Точечная инвалидация

`queryClient.invalidateQueries()` без ключа инвалидирует всё и вызывает лавину рефетчей. Инвалидируем конкретные ключи из констант.

### 7.5. Серверные данные не дублируем

Ответ не копируется в `useState` и не кладётся в контекст: кэш и есть источник правды. Один и тот же запрос не живёт на двух уровнях дерева.

## 8. Длинные списки и виртуализация

Публичный сайт редко показывает тысячи строк, но списки новостей, проектов и галереи растут.

**Правило:** список, который может вырасти за **~50–100 элементов**, обязан быть либо страничным, либо виртуализированным.

- **Сначала — серверная пагинация или «показать ещё».** Отдать 1000 карточек и виртуализировать — хуже, чем отдать 20: меньше данных по сети быстрее всего.
- **Виртуализация** (`@tanstack/react-virtual`) — когда список действительно должен прокручиваться целиком.
- Не считайте тяжёлое в рендере элемента — считайте заранее; конфигурации и колонки — вне рендера.

## 9. Сеть и кэширование

- **Кэш-заголовки статики:** хэшированные ассеты Next (`/_next/static/**`) → `public, max-age=31536000, immutable`; HTML — по стратегии страницы.
- **Сжатие** (br/gzip) на все текстовые ответы — HTML, JS, CSS, JSON. Проверьте, что прокси/CDN реально отдаёт `Content-Encoding`.
- **HTTP/2 или HTTP/3** — мультиплексирование убирает водопад запросов.
- **Меньше запросов, меньше данных:** пагинация вместо «выгрузить всё»; в списках не запрашиваем тяжёлые поля, детали грузим при открытии.
- **Отмена неактуальных запросов** при быстрой смене фильтров — `AbortController`.
- **Debounce ввода**, бьющего в API: 300–400 мс тишины вместо запроса на каждый символ.
- **Пуш/стриминг вместо поллинга** там, где нужны живые данные. На контентном сайте поллинга быть не должно вовсе.

## 10. Загрузка ресурсов и critical path

- **`preconnect`** к домену API и CDN, если они на другом origin: экономит DNS+TCP+TLS.
- **`preload` — только для ресурса критического пути** (LCP-изображение, критичный шрифт). Переусердствуете — заберёте полосу у действительно нужного.
- **`fetchpriority="high"`** на LCP-ресурс, `"low"` — на явно второстепенное.
- **Никаких синхронных `<script>` в `<head>`.** Сторонние скрипты — через `next/script` (§17).
- **Ресурсы конкретной страницы грузятся на этой странице**, а не глобально: фон одного экрана не должен предзагружаться всем посетителям.

## 11. Изображения и видео

Для сайта организации изображения — главный вес страницы и главная причина плохих LCP/CLS.

### 11.1. Только `next/image`

Он сам отдаёт AVIF/WebP, генерирует `srcset` под DPR и вьюпорт, лениво грузит и резервирует место.

```tsx
<Image src="/hero.jpg" alt="Здание офиса" width={1280} height={720} priority sizes="100vw" />
```

- **LCP-изображение (hero первого экрана) — `priority`.** Никакого `loading="lazy"` на нём: это прямой проигрыш в LCP.
- **Всё ниже сгиба — ленивое** (поведение по умолчанию).
- **`sizes` обязателен** для адаптивных изображений: без него браузер грузит слишком большой файл.
- **Размеры или `fill` + контейнер с `aspect-ratio`** — иначе CLS.
- **`alt` осмысленный**, у декоративных — `alt=""`.

### 11.2. Исходники

Не кладите в `public/` 4000-пиксельные фотографии «на всякий случай»: даже с оптимизацией это лишняя работа на сборке и в рантайме. Готовьте исходники разумного размера, SVG — для иконок и логотипов.

### 11.3. Видео

Фоновое видео на первом экране — самый частый способ убить LCP на лендинге. Если оно нужно: `preload="none"`, постер-изображение, `muted`/`playsinline`, загрузка после интерактива и отключение при `prefers-reduced-motion` и экономии трафика.

---

## 12. Шрифты

Шрифты блокируют отрисовку текста — на контентном сайте это прямо бьёт по LCP.

- **Только `next/font`** — самохостинг, автоматический `font-display: swap`, генерация fallback-метрик (это почти обнуляет CLS от подмены шрифта). Внешние `<link>` на CDN шрифтов не используем: лишний origin на критическом пути.
- **Одно вариативное начертание** вместо набора статических.
- **Подмножества — только нужные:** `subsets: ["cyrillic", "latin"]`. Греческий и вьетнамский нам не нужны.
- **Не больше двух семейств** (заголовочное и текстовое). Каждое новое — новый файл на критическом пути.
- **Preload — только для начертания первого экрана.**

```ts
import { Inter } from "next/font/google";

export const inter = Inter({ subsets: ["cyrillic", "latin"], display: "swap", variable: "--font-inter" });
```

## 13. CSS и Tailwind

- **Tailwind 4 генерирует только используемое.** Не пишите «на будущее» больших `@layer`-простыней — это мёртвый CSS.
- **`content-visibility` для длинных страниц.** Секции ниже вьюпорта можно не раскладывать, пока не приблизились:

```css
.section-offscreen {
  content-visibility: auto;
  contain-intrinsic-size: 0 600px; /* резерв места, чтобы не было CLS */
}
```

- **`contain: content`** для независимых блоков (карточки, панели) — меньше площадь пересчёта.
- **Избегайте дорогих селекторов** (`* { }`), глубоких каскадов и войн `!important`.
- **Не анимируйте свойства, вызывающие layout** (`width`, `height`, `top`, `left`, `margin`) — только `transform`/`opacity` (§15).
- Глобальный CSS держим маленьким: базовые токены и сброс. Всё остальное — утилитами рядом с разметкой.

## 14. JavaScript и главный поток

INP страдает, когда обработчик или рендер держит поток дольше ~50 мс.

- **Разбивайте длинные задачи**: уступайте потоку (`await scheduler.yield?.()`, `setTimeout(0)`, обработка чанками) или выносите в Web Worker.
- **Тяжёлый разбор/генерация данных — в Worker**, не в обработчике клика.
- **Пассивные слушатели** скролла и тача: `addEventListener("scroll", onScroll, { passive: true })`.
- **`requestIdleCallback`** для некритичного: аналитика, префетч, прогрев кэша.
- **Не чередуйте чтение и запись layout** (`getBoundingClientRect` ↔ изменение стилей) в цикле — это layout thrashing: сначала все чтения, потом все записи.
- **Проверяйте вес зависимости до установки** (bundlephobia/анализатор): ESM и tree-shaking обязательны. Часто нужное пишется двадцатью строками вместо 200-килобайтной библиотеки. Для дат — `dayjs`/`Intl`, не `moment`; из `lodash` — точечные импорты или нативные методы.

---

## 15. Анимации

- **Анимируем только `transform` и `opacity`** — они уходят на GPU-композит и не вызывают reflow.
- **Не анимируем `width`/`height`/`top`/`left`** — layout каждый кадр.
- **`will-change` — точечно и временно**, иначе растёт память слоёв.
- **Уважаем `prefers-reduced-motion`** — это и доступность, и производительность на слабых устройствах.
- **Библиотека анимаций не должна попадать в initial-граф**, если анимации есть только на внутренних экранах. Для простых появлений при скролле хватает CSS-переходов и `IntersectionObserver` — целая библиотека ради этого не нужна.

## 16. Lighthouse, SEO и доступность

### Performance (цель 90–100)

- **LCP ≤ 2.5 с**: hero-изображение с `priority`, шрифт первого экрана предзагружен, никакого lazy на LCP-элемент.
- **TBT/INP**: минимум клиентского JS (§4, §5), разбитые задачи (§14).
- **CLS ≈ 0**: размеры у изображений, `next/font` с fallback-метриками, скелетоны фиксированного размера, никаких вставок контента над уже отрисованным.
- **«Reduce unused JavaScript»**: серверные компоненты, динамические импорты, точечные импорты.
- **«Enable text compression» / «Efficient cache policy»**: brotli/gzip и `immutable` на хэшированные ассеты.

### Accessibility (цель 100)

- Осмысленный `alt` у изображений (декоративные — `alt=""`).
- Контраст текста ≥ 4.5:1.
- Все интерактивные элементы доступны с клавиатуры, видимый `:focus`.
- Иконочные кнопки — с `aria-label`.
- Корректная иерархия заголовков, один `<h1>`, `<html lang="ru">`, landmark-роли.
- `label` ↔ `input` связаны; ошибки формы объявляются ассистивным технологиям.
- `prefers-reduced-motion` уважается.

### Best Practices (цель 100)

- Только HTTPS, без mixed content; нет ошибок в консоли на проде.
- Актуальные зависимости без известных уязвимостей (`npm audit`).
- Корректные `Content-Security-Policy`, `charset`, `viewport`.
- Изображения в правильном соотношении сторон.

### SEO (цель 100 — для публичного сайта обязательна)

- Уникальные `title` и `description` на каждой странице через `generateMetadata`.
- `sitemap.ts`, `robots.ts`, канонические URL, Open Graph.
- Структурированные данные JSON-LD (`Organization`, `LocalBusiness`, `BreadcrumbList`).
- Ключевой контент приходит в HTML с сервера, а не появляется после клиентского запроса.
- Дескриптивные тексты ссылок, корректные заголовки, `lang`.

## 17. Сторонние скрипты

Счётчики аналитики, карты, виджеты чатов и соцсетей — самая частая причина, по которой быстрый лендинг становится медленным.

- Подключаем **только через `next/script`** с осознанной стратегией: `afterInteractive` по умолчанию, `lazyOnload` для всего некритичного (чаты, счётчики).
- Карта, форма стороннего сервиса, плеер — грузятся **по действию или по появлению во вьюпорте**, а не при загрузке страницы. Пока не загружены — статичная картинка-заглушка нужного размера.
- Каждый новый сторонний скрипт — отдельное решение с замером «до/после» в Lighthouse. Скрипт, который никто не смотрит, удаляем.

---

## 18. Обязательные правила для новых компонентов

Соблюдать при разработке **каждого** компонента — эти пункты действуют и вне перф-цикла (они дублируют §16 `AGENTS.md` и раскрывают его):

1. **Компонент серверный, пока не доказано обратное.** `"use client"` — на минимальном узле, максимально низко по дереву.
2. **Тяжёлое — лениво:** карта, слайдер, плеер, крупная модалка — `next/dynamic` или динамический `import()` в момент действия, со скелетоном точного размера.
3. **Скрытое не монтируется** (условный рендер вместо `display: none`).
4. **Стабильные `key`** из данных, не индекс.
5. **Нет создания объектов/массивов/функций в JSX-пропсах** мемоизированных или тяжёлых детей.
6. **`React.memo` — тяжёлым детям** со стабильными пропсами; колбэки к ним — `useCallback`.
7. **Списки > ~50 элементов** — пагинация или виртуализация.
8. **Данные — с сервера, где возможно**; на клиенте — TanStack Query с осознанным `staleTime` и `select`.
9. **Ввод в API — через debounce**, тяжёлая фильтрация — `useDeferredValue`.
10. **Изображения — `next/image`** с размерами, `sizes`, `alt`; LCP — `priority`.
11. **Шрифты — `next/font`**, новые начертания не добавляем.
12. **Анимации — только `transform`/`opacity`**, с уважением к `prefers-reduced-motion`.
13. **Никаких тяжёлых синхронных вычислений** в обработчиках и на рендере.
14. **Доступность:** клавиатура, видимый фокус, `aria-label` на иконочных кнопках.
15. **Вес новой зависимости проверен** до установки; ESM и tree-shaking обязательны.
